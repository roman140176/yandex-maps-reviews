# Отзывы с Яндекс.Карт

Laravel 13 + Vue 3 SPA: подключаете ссылку на карточку организации в Яндекс.Картах —
приложение собирает её отзывы, средний рейтинг и точные счётчики, показывает их
постранично и хранит историю изменений между сборами.

Официального API у Яндекса нет, данные добываются парсингом.

---

## Быстрый старт

```bash
git clone <repo> && cd <repo>
cp .env.example .env
docker compose up -d --build
```

Первый запуск сам сгенерирует `APP_KEY` (и сохранит его в томе `storage`, чтобы
он пережил перезапуск), накатит миграции и создаст пользователя. Через минуту
открывайте **http://localhost:8000**:

| | |
|---|---|
| E-mail | `admin@example.com` |
| Пароль | `password` |

Обе учётки задаются в `.env` (`SEED_USER_EMAIL`, `SEED_USER_PASSWORD`) — поменяйте
перед тем, как выставлять наружу. Для продакшена задайте `APP_KEY` в `.env` явно
(`php artisan key:generate --show`), а не полагайтесь на автогенерацию.

Порт занят? Поменяйте `APP_PORT` в `.env` — и заодно `APP_URL` с
`SANCTUM_STATEFUL_DOMAINS`, иначе SPA не пройдёт аутентификацию.

Вставьте в поле любую ссылку на организацию, например
`https://yandex.ru/maps/org/yandeks/1124715036/` — через ~20 секунд появятся
600 отзывов, рейтинг 4,9, 21 218 оценок и 5 859 отзывов по счётчику Яндекса.

### Что где крутится

| Контейнер | Роль |
|---|---|
| `nginx` | отдаёт SPA и проксирует PHP |
| `app` | php-fpm: API, миграции, сборка стартового состояния |
| `queue` | `queue:work` — здесь идёт весь парсинг |
| `scheduler` | `schedule:work` — регулярное обновление карточек |
| `mysql`, `redis` | данные и очередь |

### Локально без Docker

```bash
composer install && npm install
cp .env.example .env && php artisan key:generate
# для локальной разработки достаточно SQLite:
sed -i 's/^DB_CONNECTION=mysql/DB_CONNECTION=sqlite/' .env && touch database/database.sqlite
php artisan migrate --seed
npm run dev            # Vite
php artisan serve      # API + SPA
php artisan queue:work # парсинг
```

Тесты: `php artisan test` (101 тест, сеть не используется — парсер проверяется
на сохранённых ответах Яндекса).

## Как устроен парсинг

### Разведка, с которой всё началось

Прежде чем выбирать подход, я снял поведение живого источника на карточке офиса
Яндекса (5 859 отзывов):

| Что проверялось | Что оказалось |
|---|---|
| Где лежат данные | В HTML: `<script type="application/json" class="state-view">` — то самое состояние, которым гидрируется их React |
| Путь до карточки | `stack[0].results.items[0]` |
| Агрегаты | `ratingData: {ratingValue: 4.9, ratingCount: 21218, reviewCount: 5859}` |
| Отзывы | `reviewResults.reviews[]` — 50 штук на страницу |
| Пагинация | Обычный GET-параметр `?page=N` на URL `/reviews/` |
| Потолок | **12 страниц = 600 отзывов**, дальше ключ `reviewResults` просто исчезает |
| Скорость | 12 страниц за 11,8 с без пауз, без капчи |
| Дубли | 600 уникальных `reviewId`, пересечений между страницами нет |

Те самые «примерно последние 600» из задания — это ограничение самого Яндекса, а
не парсера: на 13-й странице он перестаёт отдавать блок отзывов, хотя карточка
продолжает показывать `totalPages: 118`.

### Выбранный подход: разбор SSR-JSON

Один GET на страницу, `json_decode`, типизированные DTO на выходе. Никакого
JS-рантайма, никаких токенов. **Двенадцать страниц — около 20 секунд** с учётом
троттлинга.

Что рассматривалось ещё:

**Внутренний JSON-эндпоинт `/maps/api/business/fetchReviews`.** Проверял на
практике: требует `csrfToken` (формат `hash:timestamp`, живёт в том же
SSR-состоянии) плюс сессионные cookies; на подобранном наборе параметров вернул
`400 Bad Request`. То есть страницу всё равно надо запросить первой — выигрыша
нет, а точек отказа больше: токен протухает, состав параметров недокументирован
и меняется чаще, чем форма состояния.

**Headless-браузер (Playwright/Puppeteer).** Самый устойчивый к смене вёрстки
вариант и самый дорогой: ~300 МБ образа, ~200 МБ RAM на инстанс, десятки секунд
на карточку, и ленту отзывов всё равно надо докручивать скроллом до конца. На
50 филиалах это несопоставимая стоимость при том же результате.

| | SSR-JSON (выбран) | Внутренний API | Headless |
|---|---|---|---|
| Запросов на 600 отзывов | 12 | 12 + 1 | 1 сессия + N скроллов |
| Время | ~20 с | ~20 с | 1–3 мин |
| Память | ~30 МБ | ~30 МБ | ~200 МБ |
| Зависимость от токенов | нет | csrfToken + cookies | нет |
| Хрупкость | форма JSON | форма JSON + параметры + токен | CSS-селекторы |

Риск выбранного варианта честный: мы завязаны на форму внутреннего JSON. Этот
риск снимается не надеждой, а явной проверкой контракта — см. следующий раздел.
Если Яндекс однажды уберёт SSR, отход — headless-браузер за тем же интерфейсом
`ReviewSourceParser`: меняется одна реализация, остальное приложение не знает,
откуда пришли данные.

### 1. Как парсер поймёт, что он сломался

Главное правило: **парсер никогда не возвращает тихую пустоту.** Каждый шаг
разбора — именованный якорь, и отсутствие якоря это ошибка с машинным кодом, а
не пустой результат. Молчаливое изменение на стороне Яндекса выглядит как
упавший прогон с точной причиной, а не как организация, у которой вдруг не стало
отзывов.

| Код | Когда срабатывает |
|---|---|
| `state_script_missing` | в HTML нет `<script class="state-view">` |
| `state_json_invalid` | тег есть, содержимое не разбирается как JSON |
| `results_path_missing` | нет `stack[0].results.items[0]` |
| `business_not_found` | карточка есть, но это не организация |
| `rating_data_missing` | нет блока `ratingData` |
| `rating_data_invalid` | рейтинг вне 0..5 или счётчики отрицательные |
| `review_results_missing` | счётчик отзывов больше нуля, а блока отзывов нет |
| `review_shape_mismatch` | больше 20 % отзывов страницы без обязательных полей |
| `pagination_missing` | пропали параметры постраничной навигации |
| `source_captcha` / `source_forbidden` / `source_rate_limited` | сработала антибот-защита |
| `organization_not_found` | карточка удалена (404) |

Плюс три вещи, которые ловят «данные пришли, но не те»:

**Сверка с независимым источником на той же странице.** Яндекс рендерит те же
числа ещё и микроразметкой `itemprop="aggregateRating"`. Парсер читает оба и
сравнивает: расхождение попадает в предупреждения прогона. Две независимые
реализации одних и тех же чисел — согласие между ними это реальное
доказательство, что чтение верное.

**Запрет на «пусто при непустом счётчике».** Если карточка сообщает
`reviewCount > 0`, а собрать удалось ноль — это отказ, а не успех.

**Сверка полноты.** Ожидаемое число страниц считается из счётчика отзывов и
сравнивается с фактическим; недобор фиксируется предупреждением, а не молчанием.

Всё это видно из интерфейса: у карточки есть статус, у прогона — код ошибки,
список предупреждений и прогресс по страницам. В логах те же коды
(`parsing.run_failed`, `yandex.page_failed`).

Отдельно про степень отказа: сломанная страница №7 не уничтожает страницы 1–6 —
прогон завершается со статусом `partial` и предупреждением. А вот бан обрывает
прогон сразу: продолжать долбиться в источник, который нас уже отклонил, —
худшее, что можно сделать.

### 3. Масштаб и фоновая обработка

Парсинг никогда не происходит внутри HTTP-запроса. Одна карточка — это двенадцать
последовательных запросов к источнику, который отвечает примерно за секунду;
сеть из 50 филиалов — 600 запросов.

Реализовано:

* `ParseOrganizationJob` — одна карточка, `tries=3`, `backoff=[60, 300, 900]`,
  `timeout=600`, `WithoutOverlapping` по карточке (два параллельных прогона
  одной карточки гонялись бы за одни и те же строки и удваивали нагрузку на
  источник).
* **Прогресс пишется в БД после каждой страницы** (`parse_runs.pages_done` /
  `pages_expected`), фронт опрашивает статус раз в 2 секунды и показывает
  реальный прогресс-бар, а не спиннер неизвестной длительности.
* **Повторные попытки различают причины отказа.** Смена разметки или удалённая
  карточка на третьей попытке сломаются ровно так же, как на первой, — такие
  ошибки помечают прогон `failed` сразу (`ParsingException::isRetryable()`).
  Retry достаётся только временным сбоям и банам, и с растущей паузой, чтобы бан
  успел истечь.
* `php artisan organizations:parse --all` — постановка всей сети в очередь;
  `--stale=24` берёт только те карточки, что давно не обновлялись.
* `scheduler` перепарсивает подключённые карточки раз в сутки
  (`PARSING_REFRESH_INTERVAL_HOURS`).

Для 50 филиалов это 50 задач в очереди; при одном воркере — около 20 минут,
размазанных троттлингом, вместо пика. Горизонтальное масштабирование —
добавлением реплик `queue`.

### 4. Анти-бан на объёме

Реализовано в коде:

* **Троттлинг с джиттером** — пауза 400–900 мс между страницами
  (`YANDEX_THROTTLE_MIN_MS` / `MAX_MS`). Диапазон, а не константа: ровный интервал
  сам по себе является сигнатурой бота.
* **Экспоненциальный backoff** при сетевых сбоях и 5xx — `2^n` секунд с джиттером.
* **Ротация User-Agent** из пула реальных десктопных браузеров.
* **Пул прокси** (`YANDEX_PROXIES`) с обходом по кругу и «парковкой» адреса,
  который словил отказ, на 10 минут. По умолчанию пуст — на текущем объёме
  прямых запросов достаточно; масштабирование это изменение конфигурации, а не
  переписывание.
* **Детект бана по трём признакам**: `403`, `429`, и — самое частое — `200` с
  капчей вместо карточки. Последнее критично: без этой проверки парсер бодро
  сохранил бы «организацию», вычитанную со страницы капчи. Проверяется только
  начало документа: интерстишл капчи крошечный, а настоящая карточка весит ~1 МБ
  и содержит слово «captcha» глубоко внутри аналитики.
* При бане прогон помечается `blocked`, карточка получает видимый статус, а job
  уходит на повтор с увеличенной паузой.

Что стоит добавить при реальном объёме (сейчас не сделано осознанно): общий на
все воркеры rate limiter (Redis) вместо покомандного троттлинга, распределение
карточек по времени суток, мониторинг доли `blocked` как раннего сигнала, и —
при действительно больших объёмах — резидентные прокси вместо дата-центровых.

### 5. Идемпотентность и история изменений

Повторный парсинг сходится, а не наращивает дубли:

* отзыв опознаётся по `(organization_id, external_id)` — это уникальный ключ в
  БД, так что дубль невозможен даже при гонке;
* у каждого отзыва есть `content_hash` — отпечаток значимых полей. Совпал —
  обновляется только `last_seen_at`; разошёлся — поля обновляются, а старые
  значения уходят в `review_revisions` как `{"поле": {"old": …, "new": …}}`;
* «шумные» поля (лайки, аватарка, уровень автора) обновляются молча: они дрейфуют
  сами по себе, и записывать их в историю значило бы похоронить настоящие
  изменения под тысячами бессмысленных;
* агрегаты карточки снимаются в `organization_snapshots` — по строке на прогон,
  что отвечает на вопрос «рейтинг просел — когда и с чего»;
* отзывы **не удаляются**, когда исчезают из выдачи источника. Яндекс показывает
  последние ~600, и со временем наша копия становится полнее его собственной
  выдачи — `reviews_stored` может законно превышать то, что источник отдаёт
  сегодня.

Проверено на живых данных: два прогона подряд по одной карточке — 600 отзывов до
и 600 после, 0 созданных, 0 обновлённых, 0 ревизий.

История видна в интерфейсе на вкладке «История изменений»: было → стало по каждому
изменившемуся полю, включая появление ответа организации.

## Постраничная навигация: что грузим, что кэшируем

**Отзывы отдаются из нашей БД, а не парсятся по клику.** Это ключевое решение.

Полный сбор — это 12 последовательных запросов к Яндексу и ~20 секунд. Делать
это на каждое нажатие «Далее» означало бы 20 секунд ожидания на клик, расход
лимита источника на пустом месте и приближение бана — и всё ради данных, которые
между кликами не меняются.

Поэтому: парсинг один раз в фоне → запись в БД → `GET /api/organizations/{id}/reviews?page=N`
отдаёт 50 записей из БД за единицы миллисекунд. Обновление — по кнопке и по
расписанию. Бонусом это единственный способ выполнить требование про историю
изменений: сравнивать не с чем, если ничего не хранить.

Клиент переключает страницы без перезагрузки; данные тянутся по одной странице —
грузить все 600 разом в браузер незачем.

## Архитектура

```
app/Services/Parsing/
  Contracts/ReviewSourceParser.php   интерфейс площадки (Яндекс сегодня, 2ГИС завтра)
  Data/                              DTO: профиль, отзыв, страница, результат
  Exceptions/                        иерархия отказов с машинными кодами
  Support/                           ротация UA, троттлинг, пул прокси
  Yandex/YandexUrlParser.php         ссылка → oid (чистая функция, без сети)
  Yandex/YandexHttpClient.php        HTTP: retry, backoff, детект бана
  Yandex/YandexStateExtractor.php    HTML → state JSON → DTO + проверка контракта
  Yandex/YandexReviewsParser.php     обход страниц, склейка, остановка
  ParserRegistry.php                 выбор площадки по ссылке
app/Services/Organizations/
  OrganizationConnector.php          подключение карточки и постановка в очередь
  OrganizationParseService.php       один прогон: статусы, прогресс, снимки
  ReviewSyncService.php              upsert + дифф + ревизии
app/Jobs/ParseOrganizationJob.php    очередь: tries, backoff, отсутствие наложений
```

Контроллеры про парсинг не знают ничего: валидируют, ставят задачу, читают БД.
Каждый класс проверяется отдельно — `YandexUrlParser` без сети,
`YandexStateExtractor` на сохранённых HTML, `YandexReviewsParser` на подменённом
HTTP-клиенте, сервисы синхронизации на БД.

### Схема данных

| Таблица | Зачем |
|---|---|
| `organizations` | подключённые карточки: источник, внешний id, агрегаты, статус |
| `reviews` | отзывы, `unique(organization_id, external_id)` + `content_hash` |
| `parse_runs` | прогоны: статус, прогресс, счётчики, код ошибки, предупреждения |
| `review_revisions` | «было → стало» по изменившимся полям |
| `organization_snapshots` | агрегаты на момент каждого прогона |

Рейтинги и отзывы считаются **раздельно** (`ratings_count` и `reviews_count`):
на Яндексе большинство ставит оценку, ничего не написав, — числа отличаются на
порядок, и смешивать их было бы неправдой.

### API

```
POST   /api/auth/login | logout      GET /api/auth/me
GET    /api/organizations
POST   /api/organizations                       { url }
GET    /api/organizations/{id}
DELETE /api/organizations/{id}
POST   /api/organizations/{id}/refresh
GET    /api/organizations/{id}/reviews?page=N&sort=
GET    /api/organizations/{id}/runs
GET    /api/organizations/{id}/changes
```

Аутентификация — Sanctum в SPA-режиме. Фронт отдаётся тем же приложением, поэтому
сессия ездит обычной cookie: ни CORS, ни токенов в `localStorage`, CSRF включён.

## Крайние случаи, которые пришлось учесть

Часть нашлась только на живых данных — и это самое ценное, что дала разведка.

* **Отзыв с текстом, но без оценки.** Яндекс присылает `rating: 0`, когда человек
  написал отзыв, не поставив звёзды. Первая версия парсера считала такие записи
  битыми и выбрасывала — три отзыва из 600 молча терялись. Теперь `rating`
  необязателен, а в интерфейсе такой отзыв помечен «без оценки». Обратный случай
  тоже бывает: оценка без текста.
* **Только вкладка `/reviews/` отдаёт полный первый экран.** С главной карточки
  приходит превью из трёх отзывов, поэтому любая ссылка приводится к
  каноническому `/maps/org/{id}/reviews/`.
* **Ссылки приходят в шести видах** — с `seoname` и без, с префиксом региона,
  `/profile/{id}`, `?oid=`, `poi[uri]=ymapsbm1://org?oid=`, короткие `/maps/-/XXX`
  (их приходится разворачивать редиректом), плюс домены `.ru/.com/.by/.kz/.com.tr`
  и `ya.ru`.
* **JSON внутри `<script>` не HTML-экранирован** — экранируется только `<` как
  `<`. `html_entity_decode` над этим текстом испортил бы `&` в отзывах.
* **Один битый отзыв — не повод ронять страницу**, но страница, битая больше чем
  на 20 %, — повод.
* **Float32-артефакт**: рейтинг приходит как `4.900000095367432`.
* **Несуществующий идентификатор не даёт 404.** Яндекс отвечает `200` с пустым
  результатом (`items: []`), и наивный парсер сообщил бы «изменилась разметка»,
  отправив разработчика искать несуществующий баг вместо того, чтобы сказать
  пользователю «такой карточки нет». Пустой результат при живой странице
  трактуется как `organization_not_found`.
* **Карточка может быть удалена** (404) — отдельный, неповторяемый отказ.
* **Даты приходят с миллисекундами**, а колонка хранит секунды. Без учёта этого
  каждый отзыв считался бы отредактированным при каждом сборе — история
  изменений заполнилась бы мусором за один прогон.

## Что бы доделал, будь больше времени

**Ближайшее.**
Общий на все воркеры rate limiter на Redis — сейчас троттлинг живёт внутри
процесса, и десять параллельных воркеров могут суммарно превысить темп, который
каждый по отдельности соблюдает. Это первое, что сломается при росте.

Уведомление, когда парсер перестал понимать источник: `LayoutChangedException`
пишется в лог и видна в интерфейсе, но об этом надо узнавать без захода в UI —
алерт в Slack по доле `failed` за час.

**Данные.**
Снимок «сырого» состояния при неудачном разборе (первые N КБ HTML в S3) —
починка парсера вслепую, по одному коду ошибки, занимает втрое больше времени,
чем по сохранённому телу ответа.

Полнотекстовый поиск и фильтры по отзывам (оценка, период, есть ли ответ) —
600 записей листать по 50 неудобно; это же основа для «отзывов, требующих
ответа».

**Продукт (то, ради чего эта модель и существует).**
Дифф-лента как отдельный экран: новые отзывы за период, изменившиеся оценки,
отзывы без ответа. Сейчас история есть, но подаётся как журнал, а не как
рабочий список.

Вторая площадка (2ГИС) — интерфейс `ReviewSourceParser` под это и делался;
проверка гипотезы, что абстракция настоящая, а не декоративная.

**Тесты.**
Контрактный тест, который раз в сутки ходит на реальную карточку и проверяет, что
форма ответа не изменилась, — отдельно от основного набора, который принципиально
офлайн. Это превращает «узнаем, когда сломается у пользователя» в «узнаем утром».

## Что сделано не было

* **Прототип не развёрнут на хостинге.** Требование из задания, и я его не
  выполнил: развёртывание в интернет — действие, для которого у меня не было
  ни площадки, ни разрешения владельца инфраструктуры. Всё для деплоя готово:
  `docker compose up -d --build` поднимает рабочий стенд одной командой на любой
  машине с Docker.
* Пул прокси реализован, но без самих прокси — точка расширения, не готовая
  ротация.
* 2ГИС — только интерфейс, без реализации.
* Фотографии и видео отзывов сохраняются ссылками, файлы не выкачиваются.
